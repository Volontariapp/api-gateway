# E2E scenarios: catalogue of messaging events

Business journeys that cross the async pipeline (ms-* -> event_queue -> outbox-* -> Redis Streams
-> post-processors -> ws-service -> socket). One spec per domain in this folder; shared helpers in
`helpers/` and `../helpers/`.

Sources read on 2026-11-04, `origin/main` of each repo: `npm-packages/packages/messaging/src/events/*/payloads.ts`,
`messaging/src/websockets/*/{types,mapping}.ts`, `messaging/src/sagas/gather-registry.ts`,
`shared/src/enums/streams.enum.ts`, `ws-service/config/default.config.json` (scatterGather) and
`ws-service/src/post-processors/**`, `post-processors-runner/*/src/post-processors/**`. Consumers
cross-checked with mesh-mcp `analyze_impact` (16 roots); where mesh returned 0 (stale local
checkouts), `git grep origin/main` of the named repos is the source.

ws-service runs with `NODE_ENV=test` in the stack: `GatherReaperService` is disabled
(`ws-service/src/core/services/gather-reaper.service.ts:44`), so an incomplete gather stays
PENDING forever instead of failing after 60 s. A missing runner therefore means no notification
at all, never a `*_failed` one.

## Recipients of WebSocket notifications

- **Gather (saga)**: `BaseWebSocketGatherPostProcessor.processGatherResult`
  (`ws-service/src/post-processors/base-websocket-gather.post-processor.ts:52-85`): success goes to
  the emitter (`notifyUser`, only if its socket is tracked) and to every other socket
  (`broadcastExcept`); failure goes to the emitter only. `user.deleted` goes to the emitter only,
  with `isEmitter: true`.
- **Direct** (likes, comments): `{ isEmitter: true }` to the emitter, `{ isEmitter: false }` to the
  others (`ws-service/src/post-processors/posts/interactions/post-liked.post-processor.ts:47-57`).
- **Personal** (`user.badge_awarded`, `user.impact_score_credited`, storage, jobs): `notifyUser`
  of the target user only.

## Gaps found

- **G1, event deletion saga never completed (fixed).** The EVENT_DELETION gather expected
  `social_event.deleted_success` and `post_event.deleted_success`, which no runner emits. Fixed by
  ws-service#50 (gather waits for `EVENT_SOCIAL_DELETED`, emitted by post-processor-social) and
  post-processors-runner#59. Scenario: "the organizer receives 'event.deleted'" in
  `event-scenarios.e2e.spec.ts`. Still open: no post feedback in the gather (posts of a deleted
  event, decision pending in npm-packages).
- **G2, no geocoding failure feedback.** post-processor-event logs and skips when geocoding returns
  nothing (`event-created.post-processor.ts`, after line 100): no `event.geocoding_failed`, so the
  EVENT_CREATION gather waits for the reaper (60 s, disabled in the e2e stack).
- **G3, a user deleted right after its sign-up keeps its social node.** Found by
  `user-scenarios` "ordering" (CI run 41809453352). `ms_user.event_queue`: `user.created` written
  at 09:47:45.069 but pushed at 45.158, `user.deleted` written at 45.090 and pushed at 45.150; on
  `social:user` the deletion got message id 1793785665145-0 and the creation 1793785665158-0.
  post-processor-social purged first, then created the node, which stays orphaned. Outbox rows of
  one batch are claimed with `UPDATE ... WHERE id IN (SELECT ... ORDER BY created_at) RETURNING *`
  (`npm-packages/packages/database/src/outbox/consumers/outbox.consumer.ts:31-49`): the order of
  `RETURNING` is not guaranteed (inference, not verified). Even in order, the two consumer groups
  of post-processor-social (`UserCreatedPostProcessors`, `UserDeletedPostProcessors`) can race.
- **Observations (inference, not verified at runtime).** `SAGA_GATHER_COMPLETION_MAPPING` sends the
  completion of EVENT_DELETION, POST_DELETION and USER_CREATION to their trigger streams
  (`messaging/src/sagas/gather-registry.ts:32`, `:42`, `:47`), against the rule of the
  async-event-flow skill; consumers filter by type, so the effect is extra traffic only.
  post-processor-user reads its job outbox streams without `getEventStreamName`
  (`post-processor-user/src/post-processors/options/job-outbox-success-options.ts:9`).

## Conventions

- Every scenario creates its own users (`ScenarioWorld`), coordinates (`createSuiteGeo`) and
  posts; assertions read lists scoped to that data. `ScenarioWorld.close()` deletes it.
- Never a fixed sleep: `eventually`, `waitForSocketEvent`, `recordSocketEvents`.
- Ordering scenarios use a **fence**: a later entity on the same streams proves both events of the
  first one were processed (a stream is read in order within a consumer group).
- A scenario that needs a runner missing from the stack is an `it.todo` under a `describe` named
  after the runners, never a silent skip. A system bug is an `it.failing` with its gap id.
